# Running Coach: spec

One page max. Phase 1 fills Decisions and Open risks; phase 3 finishes the rest.

## Decisions

- **License:** MIT. Permissive and standard for a public side project.
- **Domain:** the hosting provider's subdomain, no custom domain. Zero cost while there is one user; revisit if a domain is bought.
- **Free tier terms:** a card on file is acceptable if $0 is charged. In the end no chosen provider needs one.
- **History import:** first-time setup imports the user's full Garmin history so PBs cover every run; it runs as a resumable, chunked background job.
- **Hosting:** one Render free web service (0.1 CPU, 512 MB) running a single Docker image (Express serves the built SPA and the API, spawns uvicorn for the Garmin service on localhost, runs the job worker in-process behind an env flag), Neon Free Postgres, GitHub Actions cron as the daily sync trigger. Why: the only layout with no card and enforceable $0 (Render suspends instead of billing, Neon never bills); free tiers do not allow separate workers; one origin keeps session cookies simple.
- **Rejected hosts:** GitHub Pages for the SPA (github.io and onrender.com are both Public Suffix List entries, so Safari blocks the cross-site session cookie and login would need bearer tokens; its deploy step skips on PRs; revisit only if a domain is bought), Cloudflare or Vercel for the web app (same origin split, previews only the web), Cloud Run (billing account, overage), Fly, Koyeb, Railway (card or $1 credit), Render Postgres (expires after 30 days), Oracle Always Free (card, reclaims idle VMs, no subdomain).
- **Cold start:** the service spins down after 15 min idle and wakes in about 60 s; the PWA shell is precached by the service worker and shows a "waking" state until the API answers; in-app polling and the daily cron resume unfinished jobs. Why: unavoidable on free tiers, so design for it.
- **Preview deploys:** Render PR previews (previews.generation automatic in render.yaml, gated by build filters), billed at the base service's free rate; previews copy the base env and set IS_PULL_REQUEST=true, so app code switches to PREVIEW_DATABASE_URL (a separate Neon staging project) and leaves Garmin and Claude secrets empty; the URL shows as a GitHub deployment and a one-step Action comments it on the PR. Why: full-stack previews at $0; previewValue is Pro-only.
- **Build budget:** Hobby includes 500 build minutes a month and stops all builds when they run out (no billing without a card). Multi-stage Dockerfile, build filters that ignore docs and workflow-only changes, one squashed push per PR where possible, minutes checked monthly. Fallback: build the production image in GitHub Actions (free for public repos) and deploy it as a registry image, giving up Render previews.
- **Daily cron:** a GitHub Actions schedule calling a protected endpoint; it is auto-disabled after 60 days without repository activity, so Dependabot's weekly auto-merges keep the repo active and Settings shows the last daily sync time so a silent stop is visible.
- **Login:** Google sign-in only in v1, via Better Auth 1.7 mounted on Express with DB-backed session cookies and database-stored rate limiting; passkeys later as a second method. Why: every email provider needs a verified sender domain we lack; Google works with an onrender.com redirect URI in Testing mode (100 users); Auth.js now points new projects to Better Auth.
- **Origin:** web and API share one origin. onrender.com is on the Public Suffix List, so cookies cannot span subdomains.
- **iOS sign-in:** the installed PWA opens Google with a tap-synchronous window.open popup and gets the session back through a BroadcastChannel; phone-tested in phase 5; fallback is a one-time code shown after login that the app verifies. Google stays in Testing mode (100 hand-added users, "unverified app" screen) until a domain exists.
- **Garmin risk:** accepted for personal use. The client is unofficial, Garmin fingerprints TLS since March 2026, the Developer Program is business-only, and datacenter logins have been blocked. Reconnect UX ships in slice 1; phase 2 tests one login from a Render instance; if blocked, v1 connects through a local CLI that uploads the token bundle.
- **Garmin library:** garminconnect 0.3.x (Python 3.12+) with its native auth engine; garth is deprecated and unused. Pin exact versions and expect breakage within days of Garmin changes.
- **Garmin tokens:** per-user bundle is `client.dumps()` JSON (di_token, di_refresh_token, di_client_id) stored encrypted; the library refreshes automatically when the access token is under 15 min from expiry.
- **Garmin service state:** stateless for data calls (bundle in, refreshed bundle out, API writes back only when it changed, single-flight per user via a DB lock); the 2FA connect flow is two calls that hold a live session in process memory with a short TTL. Why: the MFA intermediate state is a live HTTP session that cannot be serialized; one container makes in-memory state safe.
- **Garmin politeness:** about 1 s between data calls, up to 1000 activities per page during the history import, per-user client cached for a short TTL to avoid repeated login round trips, never auto-retry 429 (login blocks last about 1 h).
- **Garmin calls:** get_activities, get_activities_by_date, get_activity, get_activity_splits, get_activity_typed_splits, get_activity_details (series + polyline), get_activity_hr_in_timezones, download_activity (ORIGINAL = FIT), get_heart_rate_zones, get_personal_record, upload_running_workout (PaceTarget), upload_strength_workout, update_workout, delete_workout, schedule_workout, unschedule_workout, get_scheduled_workouts, get_devices.
- **Garmin calendar:** the app only creates, updates or deletes workouts it created, tracked by Garmin workout ID; before scheduling a plan it lists third-party workouts in the plan window and offers to unschedule them. Why: pushing scheduled workouts overwrites the watch calendar.
- **Watch baseline:** Instinct 2 Solar on firmware 13.19+ (platform in maintenance mode): step workouts with pace, HR, time, distance or open targets and strength sets reach it via Garmin Connect; it reports HRV status, training readiness, training status and load, VO2 max, wrist running power, Body Battery and sleep; no running dynamics without a pod, no multi-band GPS, 4 to 5 data fields per screen.
- **Engine boundary:** packages/engine owns every number as pure, tested functions; Claude only selects among engine-validated session templates, writes the text, and proposes deltas the engine accepts or clamps; only the engine writes plan state. Why: plans must be safe and identical for identical inputs.
- **Engine rules (policy constants in one cited file):** paces from Daniels VDOT of the best recent race; weekly volume up at most 10% and no single run over 110% of the 30-day longest (RUNSAFE 2025), down week every 4th; at least 80% of running time easy, at most 2 quality sessions at 3 runs/week, at least 48 h between hard days; long run at most 30% of weekly volume or 150 min, whichever is stricter; per session T at most 10%, I 8%, R 5% of weekly km; taper 2 weeks (3 for marathon) cutting volume 40 to 60% while keeping intensity; minimum plan length 8 weeks for 5K/10K, 12 half, 18 marathon. When a goal needs more than the caps allow at the user's days per week, the engine reports the conflict (add a day or accept a shorter long run) instead of exceeding a cap.
- **Missed and return:** missed runs are dropped, never rescheduled; re-enter at about 70% volume after 7 days off and 50% after 14; after injury or illness a walk-run progression with a day off between runs and +10 to 30% per week until 75 to 80% of prior volume; ACWR is display-only; Riegel exponent 1.06 for predictions, with an added margin for the marathon.
- **Claude model:** default claude-opus-5-5 at effort "low" with structured outputs (output_config.format from the zod schema, thinking display omitted); fallback claude-sonnet-5-5; model is a per-user setting populated from GET /v1/models. Why: about $0.89 per user per month on Opus vs $0.44 on Sonnet for about 19 calls, paid by each user through their own key (the app bears no Claude cost), and plan advice carries injury stakes.
- **Claude plumbing:** no prompt caching or Batch API in v1 (calls are days apart, so cache writes never pay back); validate a new key with GET /v1/models (free, 401 on a bad key); max_tokens 4k for insights and 16k for plans because Opus thinking tokens cannot be disabled; check stop_reason for refusal or max_tokens before zod parsing; log usage per call including thinking tokens.
- **ORM:** Drizzle 0.45.x with drizzle-kit: SQL migrations generated and committed, applied programmatically at deploy; raw `sql<T>` for time-series aggregates; stay off the 1.0 RC until stable. Why: schema-diff migrations and a small footprint; Prisma's CLI is in flux and 74 MB.
- **Jobs:** pg-boss 12 on Postgres: sync-user with exclusive policy and singletonKey = userId, deterministic job ids (uuid v5 of user + date) so a double cron fire is a no-op, retryBackoff with jittered delays, import-history as chained chunk jobs writing a cursor row; the worker runs in the API process, with the separate entrypoint kept for local dev.
- **Encryption:** AES-256-GCM via Node crypto, 12-byte random IV, AAD = userId|column|keyVersion, per-purpose subkeys derived with HKDF from one env master key; no libsodium or pgcrypto. pino with redact paths plus a Secret wrapper whose toJSON returns "[redacted]".
- **Master key:** one 32-byte key generated at bootstrap, stored in Render's env and the owner's password manager; the key version is in every ciphertext from day one; the re-encrypt job is built when a second key is added. Why: losing the key loses every Garmin bundle and Claude key.
- **Web framework:** Vite 8, React 19, React Router 8 in data mode, vite-plugin-pwa with registerType "prompt"; not Next.js. Why: a client-only app gains nothing from Next, and static export drops its server features anyway.
- **Data fetching:** TanStack Query 5 with queryOptions factories and keys [resource, "list", filters] / [resource, "detail", id]; a thin typed fetch wrapper over a zod 4 contract map in packages/shared, response.parse() on the client. Why: ts-rest and zodios are stuck on zod 3; openapi-fetch needs a second toolchain.
- **Charts:** Recharts 3 through shadcn ChartContainer, colors as var(--chart-n), ReferenceLine for targets, animations off, 1 Hz series LTTB-downsampled to 600 points, chart screens code-split behind a 200 KB gzipped chunk budget enforced by size-limit in CI. visx is the exit if the budget breaks.
- **UI kit and tokens:** shadcn CLI 4 on Tailwind 4.3; tokens as oklch CSS variables in :root mapped through @theme inline, dark values in :root with no .dark class; defaults removed with `@theme { --color-*: initial; --text-*: initial; --radius-*: initial }` (keep white, black and the --spacing multiplier for shadcn) so only token utilities exist. Verified 2026-10-01: the compiler then refuses bg-red-500 and text-sm and the linter flags them, including hover:bg-red-500; spacing stays a 4px multiplier (p-13 is valid), and a step allowlist is added only if the first audit finds drift.
- **Map:** react-map-gl 8 (mapbox entry) with mapbox-gl 3, lazy-loaded; the maplibre entry is the exit if Mapbox terms or the 50k free loads per month bite.
- **Lint and format:** ESLint 10 flat config, typescript-eslint 8, Prettier 3 with prettier-plugin-tailwindcss; eslint-plugin-better-tailwindcss 4 with no-unknown-classes, no-conflicting-classes, no-duplicate-classes and no-restricted-classes using the arbitrary-value pattern `-\[[^\]]+\](/\S+)?$` (verified to ban text-[15px], p-[13px], bg-[#1a1a1a] and spare data-[state=open]: variants and w-(--var)), exempting components/ui/**; not Biome (its Tailwind rules are nursery).
- **Boundaries and naming:** eslint-plugin-boundaries 7 with eslint-import-resolver-typescript (web never imports api; engine and shared import no I/O or node built-ins); eslint-plugin-check-file enforces kebab-case for .ts, .tsx and .css files, component identifiers PascalCase; dependency-cruiser only in CI for cycles.
- **Versions:** exact pins (pnpm save-exact); Dependabot grouped weekly, patch and minor auto-merge when CI is green; majors (Drizzle 1.0, pg-boss, Tailwind) are a deliberate slice each.
- **Development model:** Claude Code sessions from phase 4 run claude-opus-5-5 at max effort with ultracode multi-agent workflows on; phases 0 to 3 stay on Fable. Why: build quality over token cost.
- **Hooks and toolchain:** lefthook 2 with stage_fixed and parallel for the pre-commit hook; CI runs tsc --noEmit, eslint and prettier --check. Node 24 (Active LTS until 2026-10-20, then bump to Node 26 once it is LTS on 2026-10-28), pnpm 10, Python 3.12+ with uv, ruff, mypy, pytest.

## Open risks

- Garmin may block logins from Render's datacenter IPs. Risk accepted; phase 2 tests one login from Render, fallback is the local CLI connect path.
- Refresh-token rotation and lifetimes are unverified, so a refresh race could kill a bundle. Spike 3 measures them.
- The iOS installed-PWA popup sign-in is community-verified only. Phase 5 tests it on the phone; fallback is the one-time code.
- Render documents free PR previews explicitly only for static sites and does not say Dockerfile services get previews. Phase 5 confirms a Docker web service preview costs $0 before previews are enabled, and build minutes are measured in the first month.
- 512 MB and 0.1 CPU must hold Node, uvicorn and curl_cffi. Slice 1 measures memory; fallback is a second free service for Python within the 750 hours.
- Whether Dependabot commits count as repository activity for the 60-day cron rule is undocumented. If the cron is disabled once, add a keepalive step.
- SPEC.md is over the one-page budget. Phase 3 moves the Garmin call list into the garmin-call skill and lint details into rules.
