# Running Coach: spec

## Goal and scope

A mobile-first PWA that replaces a Runna subscription for one runner first, more later. It syncs Garmin runs, builds a training plan for any goal (5K to marathon, with or without a race date), puts structured workouts on the watch, reviews each run against the plan with Claude as the coach, and adapts the plan. Each user brings their own Garmin account and Claude API key, and the owner can run the coach on their Claude plan instead; the app costs $0 to run.

## Architecture

1. `apps/web`: Vite + React PWA, served by the API from the same origin; TanStack Query over a typed fetch wrapper; Recharts; Mapbox map.
2. `apps/api`: Express + TypeScript. Routes validate with zod, call services, persist with Drizzle on Postgres (Neon). Better Auth sessions. pg-boss worker runs in the same process.
3. `services/garmin`: FastAPI wrapping `garminconnect`, spawned by the API on 127.0.0.1 and called with a shared-secret header. Stateless (token bundle in, refreshed bundle out, coarse operations: sync since date, push workout) except a pending 2FA login, held in memory for 5 min, one per user, lost on restart. Every Garmin call for a user runs under one per-user lock in the API.
4. `packages/engine`: pure TypeScript training rules, no I/O, test-first. `packages/shared`: zod contracts, error codes, units.
5. Claude: the API calls the Claude API with the user's key, versioned prompt files, structured JSON output validated with zod, fallback card when invalid. The owner can choose their Claude plan instead: the API sends the same prompt and schema to `apps/coach`, a second service that runs it through the Claude Agent SDK with the plan token, and parses the answer the same way.
6. Scheduler: a GitHub Actions cron calls a secret-protected endpoint daily, which queues one job per working login keyed on the fire's UTC date, so double fires are no-ops. Sync also runs in the request on app open (at most every 10 min) and on a Sync button; a sync asked for while one runs joins it. Each sync also lists the newest 100 runs under its login and removes stored runs Garmin no longer lists (deleted there, or no longer a run), none when more than 10 would go or the list failed or held no run; older deletions are not seen.
7. One Docker image on a Render free web service, the coach service's own image on a second; migrations run at process start; `/health`; request id flows web to API to Garmin service; problem+json errors everywhere.

## Core tables

- `user`, `session`, `account` (Better Auth); `user_settings` (user_id, units, timezone, hr_zones: the runner's max HR and five zone floors in bpm, null for Garmin's, coach_detail, claude_key_enc, coach_credential key|plan). Garmin's zones are the floors on the newest stored run, with max HR read back as zone 5's floor / 0.9 (Garmin's default 90%); before any, 50 to 90% of the highest max HR in 365 days; no Garmin call.
- `garmin_connection` (user_id, token_bundle_enc, status ok|expired, last_sync_at, last_error, garmin_records jsonb, garmin_records_at: Garmin's own PRs, stored, not shown; workouts_pushed_at, workouts_push_error, garmin_calendar jsonb: third-party workouts in the push window).
- `activity` (garmin_activity_id, user_id, type, start_utc, start_local, tz, distance_m, duration_s, avg_hr, max_hr, cadence, calories, elevation_gain_m, is_indoor, is_manual, event_type, best_efforts_version, best_efforts_attempts, best_efforts_failed_at (a run is given up after 3 tries 6 h apart), garmin_updated_at, summary jsonb); `activity_lap` (activity_id, idx, distance_m, duration_s, avg_hr, avg_cadence); `activity_stream` (activity_id, elapsed_s[], distance_m[], hr[], cadence[], elevation_m[], speed_mps[], route jsonb, hr_zones jsonb: Garmin's thinned series, track and seconds in zone, fetched once on first open; with custom zones the seconds in zone come from the stored HR series on every read).
- `best_effort` (user_id, activity_id, distance_key, time_s, start_s): each outdoor run's fastest stretch per distance, from Garmin's 1 s series fetched once per run; a personal best is the fastest row per distance.
- `goal` (user_id, one per user, kind race|fitness, distance_key, race_date, target_time_s, days_per_week, long_run_day, recent_distance_key, recent_time_s: an entered recent time); `plan` (goal_id, user_id, version, engine_version, status active|superseded, start_date, end_date, vdot, vdot_source, paces, inputs, warnings jsonb: saving the goal again makes the next version and keeps the old one with its sessions); `plan_session` (plan_id, date, type, phase, title, target jsonb, steps jsonb, status planned|done|missed|moved|skipped, activity_id, garmin_workout_id, garmin_schedule_id, garmin_date, garmin_hash; rest days have no row; a custom workout has no plan_id or phase, belongs to the user and survives a new plan version).
- `coach_message` (user_id, kind insight|weekly_review|race_plan, activity_id, plan_id, week_start, prompt_version, model, content jsonb, fallback_reason, feedback, usage jsonb; one insight per run, one weekly review per week); `import_progress` (user_id, status running|paused|failed|done, next_offset, cursor_date, last_error, resume_at, started_at, finished_at).
- `training_pause` (user_id, reason sick|injured|break, started_on, ended_on; one open per user); `plan_adjustment` (user_id, plan_session_id, source coach|review|pause|gap, kind scale|easy|rest|re_entry, outcome applied|clamped|rejected, reason, requested, applied, before, after, activity_id, coach_message_id, pause_id): every coach, review, pause and gap change to a session and every rejected coach or review proposal; run matching and the runner's own edits are not logged.

## Plan engine: rules vs Claude

- The engine owns every number as pure tested functions; Claude picks among engine-validated session templates, writes the text, and proposes deltas the engine accepts or clamps. Only the engine writes plan state.
- Rules (constants in one cited file): paces from Daniels VDOT of the best recent race; weekly volume up at most 10% and no run over 110% of the 30-day longest; down week every 4th; at least 80% easy time; at most 2 quality sessions at 3 runs a week; 48 h between hard days; long run at most 30% of weekly volume (40% at 3 runs a week, since the longest of three is at least a third; a marathon needs 4) or 150 min, and never cut below the runner's recent longest; T at most 10%, I 8%, R 5% of weekly km per session; taper 2 weeks (3 for marathon) cutting volume 40 to 60%; minimum plan 8 weeks 5K/10K, 12 half, 18 marathon.
- After each sync a run marks the session on its local date done; a past session without one is missed, stays on its date and is never rescheduled. Re-entry at 70% volume after 7 days off, 50% after 14, then each week at most 10% up until it meets the plan; after illness or injury the first 7 days are walk-run (4 min run, 1 min walk) with no quality. It applies when a pause ends ("Not feeling 100%": sick, injured, break; paused sessions leave the watch and are skipped at the end) and when a synced run follows 7 or more days without one. A pause counts the longest stretch without a run from the last run before it to the day back; a plan built during the break counts the easing its first week already carries, so one break is never eased twice. When a goal exceeds the caps at the user's days per week, the engine reports the conflict instead of bending.
- Coach, review, pause and gap changes happen in place, each logged in `plan_adjustment`; a new plan version comes only from saving the goal, since a version per run would re-create every workout on the watch. Claude may propose one change to the next session after the newest run of the last 7 days: scale 0.5 to 1.1 (a quality session loses reps or shortens them; a rise stays inside 110% of the 30-day longest, the long-run cap and +10% on the week before), easy, or rest. The engine clamps or rejects it (never a race, a custom workout, a paused session or one the coach already changed; a session a re-entry eased can only shrink), and a rejected change drops the text that depends on it. The weekly review covers the runner's last Monday-to-Sunday week once it has ended in their zone, queued by every sync (so the daily cron or the first open after it) with a job id per user and week; it may propose up to 3 such changes to the coming week's sessions, decided in date order with the week updated after each, so the week's +10% cap holds over all of them. One coach or review change per session; after a week a pause covered, no session rises. Plans stay engine-built: Claude never writes a plan (#36).
- Riegel 1.06 for predictions with a marathon margin; ACWR display-only. Paces come from the VDOT of an entered recent time, else the best race in 180 days, else the best effort of 5K or more in 90 days. A plan starts on the next Monday and covers at most 52 weeks; weeks run Monday to Sunday, the race week ends on race day; a fitness plan runs 12 weeks. Week 1 is the recent volume with re-entry applied, lifted to the smallest week the chosen days need, and more days than the 10% rule allows is a conflict.

## Decisions

- **Hosting:** one Render free web service (0.1 CPU, 512 MB) with SPA, API, Garmin service and worker in one process; Neon Free Postgres; no card anywhere. Why: the only $0 layout without separate workers; one origin keeps cookies simple. The coach on the owner's plan runs in a second free service, since Claude Code's child takes 200 to 250 MB; both sleep when idle and share 750 free hours a month.
- **Rejected hosts:** GitHub Pages, Cloudflare, Vercel (split origin breaks Safari cookies), Cloud Run (billing), Fly, Koyeb, Railway (card), Render Postgres (expires), Oracle (reclaims VMs).
- **Cold start:** 60 s wake after 15 min idle, hidden by a service-worker-cached shell and a "waking" state. After a deploy or a rollback the phone keeps the version it ran until the next screen change, and a screen that cannot read its first answer reloads once the server's version is on the phone; neither happens while a write waits for its answer.
- **No previews:** CI runs e2e and screenshots against an API started on a Postgres service with Garmin fixtures; Render builds main only. Previews return with a second contributor.
- **Deploy:** migrations at process start, expand/contract only, the HTTP contract too (`.claude/rules/contracts.md`); rollback is Render's redeploy of the previous build, and it turns auto-deploy off. Daily cron via GitHub Actions; Dependabot activity keeps it enabled; Settings shows last sync.
- **Login:** email + password via Better Auth, sign-up off, in-memory rate limits, owner seeded by CLI; Google or passkeys when other users join. Why: no third party, no redirect, works in the installed PWA; email needs a domain we lack.
- **Garmin:** `garminconnect` 0.3.x native auth (garth deprecated), pinned. Token bundle encrypted per user; access token about 24.6 h; refresh token rotates, so write back after every call and serialize per user. About 1 s between calls, never auto-retry 429. Settings connects with email, password and the 2FA code in two calls; the live login waits in the Garmin service's memory between them, since its MFA state cannot be serialized; the laptop CLI stays as the fallback. Disconnect deletes the bundle, first taking the app's workouts from today on off Garmin when asked and the login works. Details in `.claude/skills/garmin-call/garminconnect-api.md`.
- **Garmin risk:** accepted for personal use. Unofficial client, fingerprint and datacenter blocks seen; Render's IP passed in slice 1; fallbacks in the `later` issues (#13 to #19).
- **Garmin calendar:** a per-user stately job keeps today and the next 6 days (runner's time zone) on Garmin after every calendar edit, goal save, reconnect and the daily cron; ids plus a content hash and the scheduled date make a re-push a no-op, changed content is delete and re-create (`update_workout` unverified), and a batch stops at the first failure and hands back the ids it made. Run and work steps carry the zone's pace band; warm-ups, jogs and cool-downs go open. Scheduled workouts reach the watch through the Garmin Connect app sync. The app touches only workouts it created and lists third-party ones in the window with Unschedule. Moves stay in the session's week from today on and only warn about 48 h between hard days; custom workouts need an active plan for their paces.
- **Watch:** Instinct 2 Solar, firmware 13.19+: pace/HR/time/distance step workouts and strength sets; HRV, training readiness, status and load, VO2 max, running power; no running dynamics or multi-band GPS.
- **Contract:** zod only, written once in `packages/shared`; Node parses at runtime, Python validates fixtures against the exported JSON Schema. No OpenAPI codegen. The API sends only what its strict schemas declare; the web app drops response fields it does not know.
- **Claude:** claude-opus-5-5 at low effort with structured outputs; claude-sonnet-5-5 as env fallback; no caching or Batch; key validated via GET /v1/models; max_tokens 4k insights, 16k plans; check stop_reason before parsing; log usage. About $0.89 per user per month, paid by the user. **Claude plan:** the owner only (`OWNER_EMAIL`, chosen in Settings, key otherwise); the `claude setup-token` token is a secret of the coach service alone, never stored per user and never sent to the Messages API (Anthropic bans that); Claude Code runs with `tools: []`, `settingSources: []`, `persistSession: false`, an env of the token and system paths only, and 2 retries; the API wakes the service (up to 120 s) before each run (150 s), and the plan's usage limit moves the job to its reset time. A run's insight comes from an `analyze-run` job queued after a sync for its new runs from the last 7 days when a key is set (imports queue none; any other run has Ask the coach); it sees the session planned that day and the next one; a timeout or outage retries 4 times over about an hour, shown as "Coach unavailable, will retry", then the fallback card.
- **Data:** Drizzle 0.45.x with committed SQL migrations; pg-boss 12 (stately per-user sync: at most one queued and one running, deterministic job ids, chunked newest-first import); AES-256-GCM with one env key, user id as AAD, key-version prefix; pino redaction.
- **Frontend:** Vite 8, React 19, React Router 8 data mode, vite-plugin-pwa; TanStack Query 5 with `[resource, "list"|"detail", ...]` keys; Recharts 3 via shadcn, 600-point downsampling, animations off, lazy chart screens; react-map-gl 8 + mapbox-gl 3, MapLibre as exit.
- **Tokens and lint:** shadcn CLI 4 on Tailwind 4.3 with the default palette, text scale and radii removed so only token utilities exist; eslint-plugin-better-tailwindcss bans unknown classes and arbitrary values. Details in `.claude/skills/ui-component/tailwind-tokens.md`.
- **Tooling:** ESLint 10 flat config, typescript-eslint, Prettier; eslint-plugin-boundaries (web never imports api; engine and shared import no I/O); eslint-plugin-check-file kebab-case; lefthook pre-commit; Node 24 LTS, pnpm 10, Python 3.12 with uv, ruff, mypy, pytest. Exact pins; Dependabot auto-merges patch and minor except garminconnect.
- **CI:** typecheck, lint, unit and integration on a Postgres service container, Playwright e2e and screenshots in the official container with seeded fake data at an iPhone viewport, Python checks when its files change, build; auto-merge when green.
- **History:** full Garmin history, newest first, one job per page of 100 by offset in Garmin's running list (one call per page, an exact end); each page re-reads 5 list items and commits its cursor. **License:** MIT. **Domain:** host subdomain only.

## Out of scope for v1

Coach chat; sign-up for other users; Google or passkey login; custom domain; preview deploys; Strava; non-running sports; push notifications; native apps; offline editing.

## Open risks

- Garmin may start blocking Render's datacenter IPs; slice 1 synced from Render (2026-10-02). Fallbacks in issue #13.
- 512 MB must hold Node, uvicorn and curl_cffi. Slice 1 measures; fallback is a second free service.
- Anthropic changed its subscription rules five times in 2026; the coach's plan path can go at any time, and an API key in Settings is the fallback.
- Whether bot commits count as repository activity for the 60-day cron rule is undocumented; add a keepalive if it ever stops.
