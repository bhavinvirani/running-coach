# Running Coach: spec

One page max. Phase 1 fills Decisions and Open risks; phase 3 finishes the rest.

## Decisions

- **License:** MIT. Permissive and standard for a public side project.
- **Domain:** the hosting provider's subdomain, no custom domain. Zero cost while there is one user; revisit if a domain is bought.
- **Free tier terms:** a card on file is acceptable if $0 is charged. In the end no chosen provider needs one.
- **History import:** first-time setup imports the user's full Garmin history so PBs cover every run, newest first in resumable chunks, so the last year is usable within minutes and older years fill in behind.
- **Hosting:** one Render free web service (0.1 CPU, 512 MB) running a single Docker image: Express serves the built SPA and the API, spawns uvicorn for the Garmin service on 127.0.0.1 and restarts it if it dies, and runs the job worker in the same process in dev and prod (one process, no separate entrypoint). Neon Free Postgres. Why: the only layout with no card and enforceable $0 (Render suspends instead of billing, Neon never bills); free tiers do not allow separate workers; one origin keeps session cookies simple.
- **Rejected hosts:** GitHub Pages for the SPA (github.io and onrender.com are both Public Suffix List entries, so Safari blocks the cross-site session cookie; revisit only if a domain is bought), Cloudflare or Vercel for the web app (same origin split), Cloud Run (billing account, overage), Fly, Koyeb, Railway (card or $1 credit), Render Postgres (expires after 30 days), Oracle Always Free (card, reclaims idle VMs, no subdomain).
- **Cold start:** the service spins down after 15 min idle and wakes in about 60 s; the PWA shell is precached by the service worker and shows a "waking" state until the API answers; in-app polling and the daily cron resume unfinished jobs. Why: unavoidable on free tiers, so design for it.
- **No preview deploys:** CI runs the Playwright e2e and screenshot tests against a docker-compose stack inside GitHub Actions; Render builds main only, well inside Hobby's 500 build minutes a month. Previews return only with a second contributor. Why: with one developer they cost a Neon project, a secret, a CI job and a shared-staging migration trap for little proof.
- **Deploy:** migrations run at process start (expand/contract only, never a down migration), /health reports DB and Garmin-service status, rollback is Render's one-command redeploy of the previous build. Why: Render free has no pre-deploy step.
- **Daily cron:** a GitHub Actions schedule calling a protected endpoint; it is auto-disabled after 60 days without repository activity, so Dependabot's weekly auto-merges keep the repo active and Settings shows the last daily sync time so a silent stop is visible.
- **Login:** email + password via Better Auth 1.7 on Express with sign-up disabled and in-memory rate limiting; the owner account is created by a CLI seed and password reset is a CLI command until email sending exists; Google or passkeys are added when other users join. Why: no third party, no redirect, identical in Safari and the installed PWA; every email provider needs a sender domain we lack.
- **Origin:** web and API share one origin with a DB-backed session cookie. onrender.com is on the Public Suffix List, so cookies cannot span subdomains.
- **Garmin risk:** accepted for personal use. The client is unofficial, Garmin fingerprints TLS since March 2026, the Developer Program is business-only, and datacenter logins have been blocked. Slice 1 logs in from the owner's laptop with the spike CLI and uploads the token bundle; the web 2FA connect flow and reconnect UX are a later slice; phase 2 tests one login from Render, and if datacenter logins stay blocked the CLI remains the connect path.
- **Garmin library:** garminconnect 0.3.x (Python 3.12+) with its native auth engine; garth is deprecated and unused. Pin exact versions and expect breakage within days of Garmin changes.
- **Garmin tokens:** per-user bundle is `client.dumps()` JSON (di_token, di_refresh_token, di_client_id) stored encrypted; the library refreshes automatically when the access token is under 15 min from expiry.
- **Garmin service:** stateless, with coarse-grained operations (sync activities since a date, push a workout) so one login covers a batch; bundle in, refreshed bundle out, the API writes it back only when it changed; the per-user job singleton is the only lock; workout pushes are direct calls unless spike 3 shows refresh tokens rotate, in which case they go through the queue too. The later web 2FA connect flow holds a live session in process memory for two calls. Why: the MFA intermediate state cannot be serialized; one process makes in-memory state safe.
- **Garmin politeness:** about 1 s between data calls, up to 1000 activities per page during the history import, never auto-retry 429 (login blocks last about 1 h).
- **Garmin calls:** get_activities, get_activities_by_date, get_activity, get_activity_splits, get_activity_typed_splits, get_activity_details (series + polyline), get_activity_hr_in_timezones, download_activity (ORIGINAL = FIT), get_heart_rate_zones, get_personal_record, upload_running_workout (PaceTarget), upload_strength_workout, update_workout, delete_workout, schedule_workout, unschedule_workout, get_scheduled_workouts, get_devices.
- **Garmin calendar:** the app only creates, updates or deletes workouts it created, tracked by Garmin workout ID; before scheduling a plan it lists third-party workouts in the plan window and offers to unschedule them. Why: pushing scheduled workouts overwrites the watch calendar.
- **Watch baseline:** Instinct 2 Solar on firmware 13.19+ (platform in maintenance mode): step workouts with pace, HR, time, distance or open targets and strength sets reach it via Garmin Connect; it reports HRV status, training readiness, training status and load, VO2 max, wrist running power, Body Battery and sleep; no running dynamics without a pod, no multi-band GPS, 4 to 5 data fields per screen.
- **Contract:** zod only. Every API and Garmin-service response shape is written once in packages/shared; the web client and the Node API parse at runtime; the Python service validates its sanitized fixtures against the exported JSON Schema in pytest. No OpenAPI codegen or drift job. Why: one contract system; drift surfaces in pytest and at parse time.
- **Engine boundary:** packages/engine owns every number as pure, tested functions; Claude only selects among engine-validated session templates, writes the text, and proposes deltas the engine accepts or clamps; only the engine writes plan state. Why: plans must be safe and identical for identical inputs.
- **Engine rules (policy constants in one cited file):** paces from Daniels VDOT of the best recent race; weekly volume up at most 10% and no single run over 110% of the 30-day longest (RUNSAFE 2025), down week every 4th; at least 80% of running time easy, at most 2 quality sessions at 3 runs/week, at least 48 h between hard days; long run at most 30% of weekly volume or 150 min, whichever is stricter; per session T at most 10%, I 8%, R 5% of weekly km; taper 2 weeks (3 for marathon) cutting volume 40 to 60% while keeping intensity; minimum plan length 8 weeks for 5K/10K, 12 half, 18 marathon. When a goal needs more than the caps allow at the user's days per week, the engine reports the conflict (add a day or accept a shorter long run) instead of exceeding a cap.
- **Missed and return:** missed runs are dropped, never rescheduled; re-enter at about 70% volume after 7 days off and 50% after 14; after injury or illness a walk-run progression with a day off between runs and +10 to 30% per week until 75 to 80% of prior volume; ACWR is display-only; Riegel exponent 1.06 for predictions, with an added margin for the marathon.
- **Claude model:** claude-opus-5-5 at effort "low" with structured outputs (output_config.format from the zod schema, thinking display omitted); claude-sonnet-5-5 as the env-configured fallback, no per-user picker. Why: about $0.89 per user per month on Opus vs $0.44 on Sonnet for about 19 calls, paid by each user through their own key (the app bears no Claude cost), and plan advice carries injury stakes.
- **Claude plumbing:** no prompt caching or Batch API in v1 (calls are days apart, so cache writes never pay back); validate a new key with GET /v1/models (free, 401 on a bad key); max_tokens 4k for insights and 16k for plans because Opus thinking tokens cannot be disabled; check stop_reason for refusal or max_tokens before zod parsing; log usage per call including thinking tokens.
- **ORM:** Drizzle 0.45.x with drizzle-kit: SQL migrations generated and committed, applied at process start; raw `sql<T>` for time-series aggregates; stay off the 1.0 RC until stable. Why: schema-diff migrations and a small footprint; Prisma's CLI is in flux and 74 MB.
- **Jobs:** pg-boss 12 in the API process, introduced by the first slice that needs it (slice 1 syncs synchronously inside the request): sync-user with exclusive policy and singletonKey = userId, deterministic job ids (uuid v5 of user + date) so a double cron fire is a no-op, retryBackoff with jittered delays, import-history as chained newest-first chunk jobs writing a cursor row.
- **Encryption:** AES-256-GCM via Node crypto, one 32-byte env master key, 12-byte random IV, the user id as AAD, a key-version prefix in every ciphertext; the key lives in Render's env and the owner's password manager; the re-encrypt job is built when a second key is added; pino redact paths keep secrets out of logs. Why: the version prefix cannot be retrofitted; subkeys and wrappers can.
- **Web framework:** Vite 8, React 19, React Router 8 in data mode, vite-plugin-pwa with registerType "prompt"; not Next.js. Why: a client-only app gains nothing from Next, and static export drops its server features anyway.
- **Data fetching:** TanStack Query 5 with queryOptions factories and keys [resource, "list", filters] / [resource, "detail", id]; a thin typed fetch wrapper over the zod 4 contract map in packages/shared, response.parse() on the client. Why: ts-rest and zodios are stuck on zod 3; openapi-fetch needs a second toolchain.
- **Charts:** Recharts 3 through shadcn ChartContainer, colors as var(--chart-n), ReferenceLine for targets, animations off, 1 Hz series LTTB-downsampled to 600 points, chart screens lazy-loaded. visx is the exit if phone rendering or bundle size becomes a problem; no budget tooling until then.
- **UI kit and tokens:** shadcn CLI 4 on Tailwind 4.3; tokens as oklch CSS variables in :root mapped through @theme inline, dark values in :root with no .dark class; defaults removed with `@theme { --color-*: initial; --text-*: initial; --radius-*: initial }` (keep white, black and the --spacing multiplier for shadcn) so only token utilities exist. Verified 2026-10-01: the compiler then refuses bg-red-500 and text-sm and the linter flags them, including hover:bg-red-500; spacing stays a 4px multiplier (p-13 is valid), and a step allowlist is added only if the first audit finds drift.
- **Map:** react-map-gl 8 (mapbox entry) with mapbox-gl 3, lazy-loaded; the maplibre entry is the exit if Mapbox terms or the 50k free loads per month bite.
- **Lint and format:** ESLint 10 flat config, typescript-eslint 8, Prettier 3 with prettier-plugin-tailwindcss; eslint-plugin-better-tailwindcss 4 with no-unknown-classes, no-conflicting-classes, no-duplicate-classes and no-restricted-classes using the arbitrary-value pattern `-\[[^\]]+\](/\S+)?$` (verified to ban text-[15px], p-[13px], bg-[#1a1a1a] and spare data-[state=open]: variants and w-(--var)), exempting components/ui/**; not Biome (its Tailwind rules are nursery).
- **Boundaries and naming:** eslint-plugin-boundaries 7 with eslint-import-resolver-typescript as the one boundary tool (web never imports api; engine and shared import no I/O or node built-ins; api layers route -> service -> db); eslint-plugin-check-file enforces kebab-case for .ts, .tsx and .css files, component identifiers PascalCase.
- **Versions:** exact pins (pnpm save-exact); Dependabot grouped weekly, patch and minor auto-merge when CI is green except garminconnect, which is merged by hand because fixture tests cannot catch a Garmin-side break; majors (Drizzle 1.0, pg-boss, Tailwind) are a deliberate slice each.
- **Toolchain and CI:** Node 24 LTS (supported to 2028), pnpm 10, Python 3.12+ with uv, ruff, mypy, pytest. Local: docker compose runs only Postgres; the API and Garmin service run natively, the API spawning uvicorn as in production. lefthook 2 formats and lint-fixes staged files at commit; the Claude Code after-edit hook does the same on save. CI on every PR: typecheck, lint, unit and integration tests on a Postgres service container, Playwright e2e and screenshot tests in the official Playwright container against the compose stack with seeded fake data at an iPhone viewport, Python ruff/mypy/pytest when its files change, build; auto-merge when green.

## Open risks

- Garmin may block logins from Render's datacenter IPs. Risk accepted; phase 2 tests one login from Render, fallback is the laptop CLI connect path.
- Refresh-token rotation and lifetimes are unverified, so a refresh race could kill a bundle. Spike 3 measures them and decides whether workout pushes go through the queue.
- 512 MB and 0.1 CPU must hold Node, uvicorn and curl_cffi. Slice 1 measures memory; fallback is a second free service for Python within the 750 hours.
- Whether Dependabot commits count as repository activity for the 60-day cron rule is undocumented. If the cron is disabled once, add a keepalive step.
- SPEC.md is over the one-page budget. Phase 3 moves the Garmin call list into the garmin-call skill and lint details into rules.
