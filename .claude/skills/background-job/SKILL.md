# Background job

Copy `apps/api/src/jobs/sync-garmin-queue.ts`, `apps/api/src/jobs/sync-garmin.ts` and `apps/api/test/jobs/sync-garmin.test.ts`.

1. Export `name`, a zod `data` schema (sync-garmin's is the cron's `{ userId, date }`) and `jobId(data)` through `deterministicJobId(...)` from `src/jobs/boss.ts` (pg-boss ids are UUIDs), so a second send with that id returns null and runs nothing. Key the id on what makes the work unique: the user's local date for cron sends, the activity id for analyze, the plan version for push. A send without an id relies on the stately queue with `singletonKey` to fold into a waiting job. Work the runner waits to see (Sync now, the sync on app open) skips the queue: `POST /api/sync` calls the service, so its errors reach the screen. The date only keys the job: the work reads the user's current local date when it runs, so a job delayed past midnight still reaches today.
2. Handler: parse `job.data`, run under `withRequestId("job-<id>")` and call one service function. The service takes `withUserLock(userId)` and works in chunks, each committing its rows and cursor on its own, so a kill mid-way resumes.
3. Queue `{ policy: "stately" }` and `sendOptions(data)` with `singletonKey: userId` (one queued and one active per user), the id from step 1 when there is one, `retryLimit`, `retryBackoff: true`, `retryDelay`, `retryDelayMax`, `expireInSeconds` (a Garmin job: `retryLimit` 2 and `retryDelay` 300, because every attempt is a new Garmin login). A `DomainError` with code `garmin_rate_limited` is the one case where the job reschedules itself: `boss.upsert(name, data, { ...jobOptions, singletonKey: userId, match: "all", startAfter: retryAfterSeconds })` (3600 when Garmin gives none) pushes back every waiting job of the user, or queues a successor when none waits, then the job completes. A plain send would be dropped beside a waiting job, which would then call Garmin seconds after the 429. It never counts as a failed attempt. `garmin_auth_expired` and `garmin_not_connected` complete without a retry.
4. Register in `src/jobs/index.ts` (`createQueue` with the queue policy, `work` with `batchSize: 1`); expose `enqueue<Name>(data)`. Routes never enqueue: the service that queues (`startImport`, `queueDailySyncs` for the cron) imports `enqueue<Name>` from a `<name>-queue.ts` holding the queue's name, data, options and enqueue, because the handler imports the service (`src/jobs/sync-garmin-queue.ts`, `src/jobs/import-history-queue.ts`).
5. Test on the real Postgres with the fixture Garmin service: the cron runs once per date however often it fires; the next date's send after a completed run queues again; a send folds into a job already waiting; a second run stores nothing more; resumes from the cursor after a thrown error; a 429 defers a waiting job without a failed attempt; an expired login completes without retrying; two concurrent runs for one user share one Garmin sync (single-flight) and serialize with another process holding the lock.
