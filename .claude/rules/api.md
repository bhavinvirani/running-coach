# API (apps/api)

## Layout

- `src/routes/<resource>.ts`: one Express router per resource. Parse `req.body`, `req.params` and `req.query` with `parse(schema, value)` and schemas from `@running-coach/shared`, call one service function, send through `respond(res, schema, data)` (both in `src/lib/http.ts`) so the output is parsed too. No database access, no fetch, no business logic in a route.
- `src/services/<name>.ts`: business logic and the only layer that uses `db`, `garminClient` or `coach`. Functions take plain arguments, return plain data, throw `DomainError`.
- `src/jobs/<name>.ts`: pg-boss handlers (background-job skill). `src/garmin/client.ts`: the only caller of the Python service; `src/garmin/process.ts` spawns it and restarts it with backoff. `src/coach/`: the only caller of Claude. `src/auth/`: Better Auth, its handler, `requireUser` and the cron's `requireCronSecret`. `src/lib/`: `errors.ts`, `logger.ts`, `crypto.ts`, `config.ts`, `http.ts`, `locks.ts`, `lock-key.ts`, `rate-limit.ts`, `lifecycle.ts` (readiness checks, shutdown hooks), `paths.ts`, `local-date.ts`.
- One process: `src/index.ts` boots in order config (validated on import) → migrations → owner seed (when `OWNER_*` are set) → Garmin service child process → pg-boss and its workers → listen, and shuts down in reverse. `/health` answers 200 `{ status, dependencies }` once listening, also while the Garmin child restarts, and 503 naming the dependency once the child has been down longer than 3 min (`downGraceMs` in `src/garmin/process.ts`). A separate worker entrypoint is deferred (#16).
- Jobs: pg-boss queues with policy `stately` and `singletonKey: userId` (one queued and one active per user). `sync-garmin` is the daily cron's alone: `POST /api/cron/sync` (`src/services/daily-sync.ts`) queues one per user whose login is `ok`, with an id keyed on the fire's UTC date, never the user's local date, which two fires can share near DST or a late run (`deterministicJobId` in `src/jobs/boss.ts`, through `src/jobs/sync-garmin-queue.ts`), so a double fire is a no-op; expired and missing logins get none. Sync now and app open do not enqueue: `POST /api/sync` calls `syncGarmin` under the same user lock and answers with the outcome, so a 409, 429 or 502 reaches the screen that asked instead of hiding behind job retries. `syncGarmin` is single-flight per user in the process: a sync asked for while one runs (a tap during the open sync, the cron job during either) joins it and shares its outcome. `import-history` runs one page of the full-history import per job and queues its successor with an id keyed on the import's start and the new offset; `POST /api/import` queues the first page or a resume without an id, so the stately queue folds it into a waiting page. `best-efforts` is queued without an id after each sync, in each import page's transaction and at boot while due runs have no waiting or retrying job, and each batch of 10 runs queues its successor 30 s later while runs are due (one Garmin login per batch). An outage marks no run done and counts no try, and pg-boss retries; the canary and the 6 h spacing of failed runs are in the doc comment on `computeBestEffortsBatch`. `push-workouts` (`src/services/workout-push.ts`) keeps today and the next six local days on Garmin: it diffs each session's stored Garmin ids, date and content hash against what it should be (`planWorkoutPush` in `src/services/workout-push-plan.ts`, pure), sends at most 8 actions per `POST /workouts/sync` in up to 5 rounds, stores each result with `db` at once so a later throw keeps the ids, and turns a batch's `stopped` into the client's error so the 429 gate and the retries work as for sync; every session change, a goal save and a reconnect queue one without an id (stately folds them), the daily cron one keyed on the fire's UTC date. Other jobs key the id on what makes the work unique (background-job skill).

## Errors

- Expected failures throw `new DomainError(code, status, detail?, { retryAfterSeconds?, cause? })` with a code from `packages/shared/src/error-codes.ts`. Never throw strings or bare `Error` for expected cases.
- One middleware in `src/lib/errors.ts` renders problem+json `{ type, title, status, code, detail?, requestId, retryAfterSeconds?, issues? }`, with a `Retry-After` header when `retryAfterSeconds` is set. Unknown errors become 500 with code `internal`, logged with the stack; the response never includes a stack or an upstream message. zod failures at the edge become 400 with code `validation` and `issues` `[{ path, message }]`.
- 401 means only "no session" (the web app logs out on it), or a wrong secret on the cron endpoint: Garmin login problems (`garmin_auth_expired`, `garmin_not_connected`) are 409.

## External calls

- Garmin service: timeout 60 s for sync, history pages, an activity's detail (a login plus three paced calls) and a best-efforts series batch, 20 s otherwise; the client retries twice with backoff and jitter only when the service gave no answer (`fetchJson` with `retryOn: "network"`), never on any answer or a timeout, because the service already retried Garmin and every request is another Garmin login; slower retries belong to the job (`retryLimit` 2, `retryDelay` 5 min with backoff). A 429 is never retried immediately: the client throws `garmin_rate_limited` with `retryAfterSeconds`, and only a job defers itself, with `boss.upsert(..., { singletonKey, match: "all", startAfter })` (background-job skill). Every call for a user runs inside `withUserLock(userId)` from `src/lib/locks.ts` (a transaction-scoped Postgres advisory lock taken on its own small pool, so waiting callers never hold the app pool's connections); when the bundle in a response, or in a Garmin-service error's `tokenBundle`, differs from the one sent, write it back before releasing the lock. The one exception is the connect proof (`PUT /api/garmin/connection`), which stores nothing on failure: a bundle from a fresh login does not refresh on its first call. A `garmin_rate_limited` failure starts an hour in which every Garmin call for the user (sync, import page) refuses with the remaining `retryAfterSeconds` without calling Garmin, because each try during a block is another login; the gates, the bundle write-back and the failure bookkeeping live in `openGarminAccount` (`src/services/garmin-account.ts`).
- Claude: timeout 60 s (`CLAUDE_TIMEOUT_MS`); one retry with jitter on 429, 529, 5xx or a dropped connection, on the fallback model; never on a timeout. Details in the coach-prompts rule.
- Every outgoing request carries `x-request-id` from the current request, or `job-<id>` in a job (`withRequestId`).

## Config and secrets

- `src/lib/config.ts` reads every env var once through a zod schema and exits at boot on a missing or invalid value. Nothing else reads `process.env`; the Garmin child gets only the allowlisted system variables from `inheritedEnv()`.
- `encrypt(plaintext, userId)` / `decrypt(ciphertext, userId)` in `src/lib/crypto.ts`: AES-256-GCM with `MASTER_KEY`, the user id as AAD, `v1:` prefix on the ciphertext. Decrypt inside the service function that needs the value and never return a secret from a route, not even masked.
- Logger: pino, JSON lines, `redact` for `tokenBundle`, `token`, `password`, `apiKey`, `authorization`, `cookie`, `set-cookie`, `email`, `x-garmin-secret`; `errSerializer` (logger and pino-http) strips SQL params and pg `detail` from an error and its causes. Print an error outside the logger only through `safeErrorMessage`. Log ids, counts and durations, never activity payloads.

## Auth and limits

- Better Auth owns `/api/auth/*` through `src/auth/handler.ts`, which turns its errors into problem+json; sign-up is off. Boot creates a missing owner from `OWNER_*` and never changes an existing one; `pnpm seed:owner` resets the name and password and signs out the owner's sessions. Every user gets its `user_settings` row at creation (`databaseHooks.user.create.after` in `src/auth/auth.ts`), so readers never default missing settings. Every other `/api` route sits behind `requireUser` in `src/routes/index.ts` and reads `req.user.id`; no route accepts a user id from the client.
- In-memory rate limits on `/api/auth/*` (10 per 60 s per client IP from `req.ip` with `trust proxy` 1, `/get-session` exempt, on in every `NODE_ENV`) and `/api/sync`, `/api/garmin/connection`, `POST /api/import`, `POST /api/activities/:id/detail`, `POST /api/calendar/push` and `POST /api/calendar/unschedule` (6/min/user each, because each one logs in to Garmin or queues a login). The cron endpoint (`src/routes/cron.ts`, mounted above `requireUser`, its guard in `src/auth/require-cron-secret.ts`) takes `Authorization: Bearer <CRON_SECRET>`, compares SHA-256 digests with `timingSafeEqual` and answers 401 `unauthorized` to anything else; `CRON_SECRET` is required in production, and the endpoint has no rate limit because a wrong secret does no work.
- CORS: `APP_URL` only, credentials on. Helmet defaults. JSON body limit 1 MB. Every `/api` response is `cache-control: no-store`.

## Serving the SPA

- Static files from `apps/web/dist`: immutable cache for hashed assets, `no-cache` for `index.html` and the service worker; unknown non-API paths return `index.html`.
