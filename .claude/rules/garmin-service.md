# Garmin service (services/garmin)

- FastAPI on uvicorn bound to 127.0.0.1, started by the API as a child process; it exits when `GARMIN_PARENT_PID` is gone. Every request carries `x-garmin-secret`; a mismatch is 401 before any other work. Never reachable from the public port.
- Stateless except one pending 2FA login per user: each request body carries `tokenBundle` (the decrypted JSON string) and every response returns `tokenBundle`, refreshed or unchanged; an error carries it too when login rotated it. No file tokenstore, no module-level client, no cache across requests. A password and 2FA code are accepted in two places, both through `garmin_service/password_login.py`: the laptop CLI `garmin_service/connect_cli.py` (`pnpm garmin:connect`), which keeps them in memory and hands the API only the bundle, and the web flow's `POST /connect` and `POST /connect/mfa`. When Garmin asks for a code, `/connect` keeps the live `Garmin` instance (its MFA state is an HTTP session, not serializable, the password cleared from it) in process memory (`pending_logins.py`, created per app in `create_app`): one per `loginId` (the API sends the user id), a new start replacing it, 5 min from the start, at most 3 refused codes, nothing on disk. A restart or deploy empties it: `garmin_login_lost`. uvicorn runs one process (the API spawns it without `--workers` and passes no `WEB_CONCURRENCY`), so there is one store.
- Coarse endpoints, one per use case (`POST /profile`, `POST /sync` (plus, on request, the ids of the newest runs from `get_activities` in the same login, so the API can drop runs deleted on Garmin), `POST /history` (a page of the full-history import by offset), `POST /activities/{id}/detail`, `POST /activities/series` (up to 10 runs' 1 s time and distance samples for best efforts, plus Garmin's own records on request), `POST /workouts/sync` (up to 8 create, move, remove or unschedule actions under one login, then the calendar; a failure after login answers 200 with each action's outcome and `stopped`), `POST /connect` (email and password: `code_needed`, or `connected` with the bundle), `POST /connect/mfa` (the code, tried on the pending login: the bundle; one code at a time per login)), not one per library method. Every library call goes through `GarminSession.call` in `garmin_service/client.py`, which keeps `GARMIN_CALL_GAP_S = 1.0` between calls; the one exception is the password login of the CLI and `/connect` (`login()`, then `resume_login()` after the runner types the code), two calls a person already spaces, neither retried, each answering a bundle only when it holds both DI tokens. The library retries 5xx and network errors on data calls (`GARMIN_RETRY_ATTEMPTS = 2`), never on the workout writes, which go out once, nor on `/workouts/sync`'s calendar read (`GarminSession.call_once`), so the batch fits the API's timeout; the API client retries only when the service gave no answer (`retryOn: "network"`), so an answer from here is final for that request. A 429 from Garmin is returned as 429 with `retryAfterSeconds` and never retried here.
- Errors: problem+json with the shared codes (`garmin_auth_expired`, `garmin_rate_limited`, `garmin_unavailable`, `garmin_mfa_required`; for the password login `garmin_credentials_rejected` 422, `garmin_mfa_rejected` 422 with the login kept, `garmin_login_lost` 409 when the login is gone: none pending, the third code refused, or Garmin accepted the code and the login failed after it). Library exceptions are mapped in one place, `services/garmin/garmin_service/errors.py`, by their cause chain, never by the outer class; a password login reads an auth error as what the runner typed (`from_login_exception`, `from_code_exception`), except a failed code check, whose message lists each verify endpoint's outcome: a 429 on either is `garmin_rate_limited`, no answer from both (network error, non-JSON page) `garmin_unavailable`, a refusal on either `garmin_mfa_rejected`. On `/connect/mfa` a 502 always means the login waits (an outage while the library's MFA session survived), a 429 drops it.
- Models: pydantic v2 in `garmin_service/models/` on `RequestModel` and `ResponseModel` from `models/base.py`, snake_case fields with camelCase aliases on the wire. The zod schema in `packages/shared` is the contract; `tests/test_contract.py` validates every response built from the fixtures against the exported JSON Schema.
- Library facts (token rotation, method names and arguments, workout model, error chains) live in `.claude/skills/garmin-call/garminconnect-api.md`. A method not listed there gets added to that file in the same PR, with what was verified.
- Tests: pytest against the app with the `Garmin` client replaced by `garmin_service/fake_client.py` serving `tests/fixtures/*.json` (`ScriptedGarmin` in `tests/helpers.py` for cases the files do not cover, `FakeLogin` for a password login's, `WaitingGarmin` for the library's own code check over a scripted MFA session). Fixtures are produced by `tests/sanitize.py` from raw captures in `services/garmin/raw/` (git-ignored) (ids and serial numbers renumbered; names, free text, emails and URLs replaced; birthDate, age, gender, weight and height faked; locations, coordinates, polylines and profile images removed; timestamps and metrics kept, so read them); a raw Garmin response is never committed. The hand-made fixtures are `history.json` (fake years before `sync.json`, one account with it), which `test_sanitize.py` checks with its ids and names exempt, and `personal-records.json` (made-up records in the captured shape); one value in `sync.json` is hand-set, the 10.2 km run's `eventType` (`typeKey` race, `typeId` 1 unverified against Garmin), so the fake account holds a race. The detail fixtures (`detail-splits.json`, `detail-series.json`, `detail-hr-zones.json`) are one run, sanitized and then trimmed (laps to the mapped keys, the series to 8 columns and every 3rd row, coordinate columns dropped by hand) and re-sanitized; `FakeGarmin` serves them for every id of the account and derives the treadmill, no-HR and manual variants from its list item. The workout fixtures (`workout-upload.json`, `workout-schedule.json`, `workout-calendar.json`) are spike 2's captures (2026-10-01), sanitized; by hand the calendar was trimmed to its eight workouts and one activity, their `id`s renumbered (the sanitizer leaves a bare `id` alone: `detail-series.json` uses it for unit ids), titles replaced with generic ones and dates spread over days 1 to 26, so `FakeGarmin`, which moves them into whatever month is asked for, has one in every 7-day window. `GARMIN_FIXTURES=1` makes the service serve the same fake for the API's integration tests and e2e, and `FakePasswordLogin` for `/connect` (any email with `fixture-password`, code `123456`, `rate-limited@example.com` a 429, `no-code@example.com` no code; the base bundle).
- Tooling: uv, ruff format and lint, mypy strict, Python 3.12. `garminconnect` pinned exactly and excluded from Dependabot auto-merge.
- Logs: JSON lines with the `request_id` from `x-request-id`; never the bundle, email, password, MFA code or activity payloads.
